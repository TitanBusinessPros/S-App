# Survival Day

A wilderness survival guide app. Note: signing in (Google Sign-In) requires an internet connection — it is not offline-first, though a number of individual features work without a live connection once you're signed in and have opened the app at least once. See "On credentials" and each feature's own notes below for what actually needs a connection and what doesn't.

## Sibling apps sharing this backend

As of 2026-09-12, **this is the only repo that may own backend deploys** for the Firebase project `survival-day-app`. A second repo, [`S-App-2-Language`](https://github.com/TitanBusinessPros/S-App-2-Language), is a frontend-only duplicate of this app's `web/` workspace — a starting point for a localized/second-language variant — that deliberately shares this same Firebase project by explicit decision: same Auth users, same Firestore data/entitlement (a subscriber here is automatically a subscriber there, no separate paywall), and the exact same deployed Cloud Functions. It deploys to its own Hosting site (`survival-day-2-language.web.app`, a second site inside this same project) and has no `functions/`, `firestore.rules`, or `storage.rules` of its own.

**Practical implication for future work here:** a Cloud Function rename/removal, a Firestore schema/field change, or a Firestore/Storage rules change made in *this* repo can affect that app too, since it calls the same deployed backend. There's no CI or test coverage in this repo that would catch that — check `S-App-2-Language`'s `web/src` for usages before renaming or removing anything backend-facing that isn't purely internal to this app's own UI.

## Session Status (as of 2026-09-09 CDT)

This section exists so a new session (human or Claude Code) can pick up exactly where the last one left off. It intentionally contains **no credentials or secrets** — see "On credentials" below for why.

### What's built and deployed
- **Foundation**: Google-only sign-in (no email/password), dark UI shell, tiered access (`trial` → `free`/`premium`/`gold`) computed client-side via `web/src/lib/entitlement.ts`. Once the 3-day trial ends (and absent a `premium`/`gold` tier), every feature locks except **Compass** and **First Aid**, which stay free permanently: `components/PaidFeatureRoute.tsx` redirects a locked route straight to `/app/upgrade` (so direct URLs/bookmarks can't bypass it either), and `Dashboard.tsx` shades locked feature cards and points their links at the same pricing page instead of the feature. The two Cloud-Function-backed paid features (`getWaterFeatures`, `getSpeciesNearby`) also enforce this server-side via `functions/src/entitlement.ts`'s `requirePaidAccess` — re-reading the caller's own Firestore tier and rejecting with `permission-denied` — so calling those functions directly, bypassing the UI entirely, can't return real data to a locked account either. The remaining locked pages (Shelter, Finding Water, Snares, Fire Starting, Water Purification, Waypoints, Recipes) are still UI-gated only, since their content is static data bundled into the client either way, not fetched per-request from anything that could check a tier.
- **Billing**: Stripe is fully wired up — $12/year via a Stripe Payment Link (`web/src/lib/stripe.ts` builds the checkout URL), `stripeWebhook` Cloud Function keeps each user's Firestore tier in sync with their subscription, `grantGoldMembership`/`backfillTrialTiers` are admin-only callables for manual grants and one-time migrations. New sign-ins get a 3-day trial (`TRIAL_DURATION_MS` in `functions/src/constants.ts`)
- **Analytics** (2026-09-09): Firebase Analytics is wired in via the same modular `firebase` npm SDK the app already uses elsewhere — `firebase.ts` exports `analyticsReady` (an async `isSupported()` check first, so it resolves to `null` instead of throwing wherever Analytics isn't available: private browsing, this app's own jsdom test suite), `lib/analytics.ts` has fire-and-forget `trackEvent`/`trackPageView` helpers, and `components/AnalyticsPageViews.tsx` logs a `page_view` on every route change (Analytics only auto-logs one on the initial script load, and this is a client-routed SPA). Privacy Policy and Terms of Service were updated in the same change, since they previously stated the app used no analytics/trackers at all.
- **Compass**: magnetic heading (phone only) + star-compass (Polaris) guidance
- **Waypoints & Trail**: drop a pin, record a GPS breadcrumb trail back to it, all local (device GPS + local storage, no backend). The "You" marker tracks your live position continuously — during recording (fed by the same GPS watch) and after you stop (a separate watch takes over automatically) — plus a "📏 Off trail" readout (distance to the nearest point on the recorded path, not just to the start pin) and a trail-map frame that only grows, never rescales on every GPS tick, so movement reads as real motion instead of looking frozen. The trail's start point also self-corrects if a much more accurate GPS fix arrives within the first few seconds. A 3-step "how to use this" guide sits at the top of the page.
- **Water & Terrain Map**: adjustable-radius water search via USGS's 3D Hydrography Program (3DHP), through a Cloud Function; the map background is USGS's public-domain USGSTopo raster tiles (`MapWater.tsx`'s `BASEMAP`), no API key/billing. A vector-tile "street" option (OpenFreeMap, via the MapLibre GL Leaflet binding) was tried and removed after it rendered blank in practice — see git history (the `openfreemap-basemap` and `fix-openfreemap-blank-canvas` commits, then its removal) if that's ever revisited; USGSTopo alone is the live basemap now. Lookups are manual and rate-limited: a "Scan for Water" button next to "Re-center on me" is the only way to trigger a search (nothing auto-fetches on load, location change, or radius change anymore), and each press costs 1 of `DAILY_WATER_SCAN_LIMIT` (3) credits per rolling 24h window — enforced server-side in `getWaterFeatures` itself (`functions/src/waterScanCredits.ts`), not just hidden client-side, so it can't be bypassed. Credits are tracked per-user in `waterScanCredits/{uid}`, readable by that user only. The page itself stays lazy-loaded (`React.lazy` in `App.tsx`) since it's a reasonable performance win on its own, independent of the basemap.
- **3D Maps** (`Map3D.tsx`, `/app/map3d`): a tilted, rotatable 3D view of the user's location with a "you are here" pin, using OpenFreeMap's Liberty style rendered via plain MapLibre GL directly (no Leaflet involved this time) — the same style/tile service the removed "street" basemap used, but a different integration path deliberately chosen to avoid the Leaflet-binding bug that broke that one, and because the Leaflet binding can't do pitch/bearing at all, which a 3D view requires. "3D" isn't a distinct OpenFreeMap product — it's the same flat vector style viewed at a pitch (60°) and bearing (55.2°), matching OpenFreeMap's own demo values, just recentered on the user instead of a fixed London default. Any load failure (WebGL unavailable, a hung fetch, a construction error) is shown directly on the page instead of an unexplained infinite "Loading map…", since there's no way to see a user's own browser console from here — this is what surfaced the real bug: MapLibre GL needs an explicit `setWorkerUrl()` pointer under Vite (`import ... from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url'`) or its background tile-parsing worker silently never loads, hanging forever with no thrown error at all. 3D building extrusion depends on OpenStreetMap having height data traced for a given area — reliable in dense city centers, often absent elsewhere; that's a data-coverage gap, not a bug.
- **Moon Phase** (`moonPhase.ts`, `/app/moon-phase`): current phase, illumination %, and next full/new moon dates, from a pure client-side synodic-cycle calculation (no API, no location, fully offline, accurate to roughly ±1 day). First of the "costs nothing" feature ideas brainstormed this session to actually get built.
- **SOS Beacon** (`morseCode.ts`, `SosBeacon.tsx`, `/app/sos-beacon`): flashes the screen and plays a tone in Morse code SOS, in sync, on a loop. Uses the Web Audio API for the tone (no audio file) and the screen itself rather than the camera flash (no camera permission needed, works identically everywhere, unlike the flash API which barely works cross-browser). Requests a screen wake lock while running so the display doesn't sleep mid-signal; degrades gracefully if unsupported. Second of the "costs nothing" feature ideas to get built.
- **Topography Map** (`TopographyMap.tsx`, `topoGuideData.ts`, `/app/topography`): the same USGSTopo basemap as the Water & Terrain Map, centered on the user with a "you are here" pin, plus an extensive from-scratch guide to actually reading contour lines (basics/contour interval, terrain shapes, slope & steepness, practical route-finding uses, common misreadings — all original wording, not adapted from any specific copyrighted source, since the underlying cartographic concepts are standard/public-domain knowledge). `TOPO_BASEMAP`/`meIcon`/`RecenterMap` were extracted out of `MapWater.tsx` into `lib/leafletTopo.ts` so both map pages share one definition — Rollup automatically factors Leaflet itself into one shared chunk between the two lazy-loaded pages rather than bundling it twice.
- **Solunar Calculator** (`solunar.ts`, `SolunarCalculator.tsx`, `/app/solunar`): predicted major (~2h, moon overhead/underfoot) and minor (~1h, moonrise/moonset) wildlife-activity periods for today, based on the century-old public-domain solunar theory. `solunar.ts` computes the moon's actual position from scratch (standard low-precision orbital-mechanics formulas, no perturbation-term corrections, original implementation — not adapted from any specific commercial solunar app) and finds each event by numerically sampling altitude/hour-angle across the day rather than solving for them analytically. Verified directly against a real published moon almanac (usairnet.com) across three different dates spanning different points in the lunar cycle before shipping — all three landed within 1–6 minutes of the reference, well inside the ±30–60 minute accuracy the page discloses to users. No API, no location cost — same "costs nothing" spirit as the rest of this batch.
- **Search** (`searchIndex.ts`, `Search.tsx`, `/app/search`): a single search bar across First Aid, Finding Water, Shelter, Snares & Traps, Topography, and Recipes content, with an optional voice-input button using the browser's built-in `SpeechRecognition` where supported (feature-detected — notably absent in Firefox — the button just doesn't render rather than being a dead click target). Plain case-insensitive substring matching over a flat index built once from the app's own existing structured data files, not a search library. Water Purification and Fire Starting aren't indexed yet since their content still lives inline in their page components rather than an extracted `*Data.ts` file the way the other guides do — a known gap, not an oversight.
- **In-app update prompt** (`UpdatePrompt.tsx`): the PWA previously had no way to get already-installed users onto a new deploy short of them fully closing and relaunching the app — `registerType` was `autoUpdate` but the service worker was never actually registered through `virtual:pwa-register`, so nothing ever prompted or auto-reloaded. Switched to `registerType: 'prompt'` with `injectRegister: false`; `UpdatePrompt.tsx` registers the service worker itself via `virtual:pwa-register/react`'s `useRegisterSW` and shows a small "Refresh to update" banner once a new version has downloaded in the background. Also explicitly calls `registration.update()` right when someone logs in, rather than only relying on the browser's own background check interval, since that moment is the one most likely to actually be seen.
- **Visible build version stamp** (`Footer.tsx`): `vite.config.ts` embeds the current git short commit hash as `__BUILD_ID__` at build time; the footer shows it as "Version \<hash\>" on every page. Exists specifically so "did my deploy actually reach your device" has a one-glance answer instead of a guess — added after several rounds of a deployed fix not being visible to a real user despite passing every server-side check this session had available.
- **Field Guides** — First Aid, Shelter Building, Finding Water, and Snares & Traps were each rebuilt around much larger structured reference content (see "Major content overhaul" below); Fire Starting and Water Purification (25 improvised filters) are unchanged. All are general reference content, deliberately not tied to fabricated per-location claims.
- **Plants, Wildlife & Wood**: a small hand-curated starter dataset (~24 Oklahoma species), cross-checked against real GBIF occurrence data and filtered by real season windows, via a Cloud Function. As of 2026-09-09, lookups are manual and rate-limited the same way as the Water & Terrain Map: a "🔍 Look Up Nearby" button (nothing auto-fetches on mount or on radius/month change anymore) costs 1 of `DAILY_SPECIES_LOOKUP_LIMIT` (3) credits per rolling 24h window, enforced server-side in `getSpeciesNearby` itself (`functions/src/speciesLookupCredits.ts`) against its own `speciesLookupCredits/{uid}` Firestore doc — a separate credit pool from water scans. The rolling-window transaction both features share now lives in `functions/src/dailyCredits.ts` (`waterScanCredits.ts` was refactored to delegate to it too, same public API).
- **Legal/site polish**: Terms of Service (18+ eligibility, trapping/hunting/fishing regulatory language), Privacy Policy (18+ age requirement), shared footer, real app icon as favicon
- Section/card headers are centered consistently app-wide (deliberately excluding repeated per-item list cards like recipe/species cards, and the Terms/Privacy numbered legal sections — see the `center-section-headers` PR for the reasoning)
- Everything above has Jest/Vitest tests and is enforced by CI (100% Cloud Function test coverage is a hard gate — see `testing/functions/check-coverage.js`)
- Deployed live: **https://survival-day-app.web.app** (Firebase Hosting + Cloud Functions + Firestore, project `survival-day-app`, Blaze plan)

### Major content overhaul (2026-09-06)
Four Field Guide pages were rebuilt from short hand-picked sections into much larger structured references, each provided directly by the user and each following the same pattern: content lives in a `web/src/lib/*Data.ts` file (not inline in the component) with its own data-integrity test (sequential numbering, no gaps/duplicates, every field non-empty), and the page just maps over it.

- **First Aid** (`firstAidData.ts`): a 7-point "Universal Response" checklist + 100 problem→action rows across 4 categories, rendered as a responsive table.
- **Shelter Building** (`shelterData.ts`): a 5-part "Universal Shelter Rules" checklist + all 15 shelter designs (full build steps, key details) + a "things I would not recommend" list.
- **Finding Water** (`findingWaterData.ts`): "First Priorities" + 50 numbered methods across 3 categories, a dedicated "how to dig a seep hole" procedure, a "methods to avoid" table, and a treatment-methods comparison table (boiling/filter/chemical/UV/settling).
- **Snares & Traps** (`trapDesignsData.ts`): kept the pre-existing wire-loop/noose snare designs (Squirrel Pole, Rabbit Run Snare, Twitch-Up Spring Snare — genuinely not covered by the new material) and added 100 primitive trap/live-capture/aquatic-trap designs across 4 categories, each a collapsed-by-default `<details>` card (100 always-open cards would be unusable on a phone).

Each rebuild included an explicit **duplicate/contradiction check** against the page it replaced, not just an addition — e.g. Finding Water's old "Solar Still" how-to and "animal trails are a water indicator" claim were both *removed*, not kept alongside, because the new source material explicitly lists them as failure-prone/methods to avoid.

Shared UI patterns that came out of doing this 3-4 times: `.guide-table`/`.guide-nav`/`.guide-subheading` in `web/src/components/GuidePage.css` (promoted there after First Aid, Shelter, and Snares each needed the same responsive table/nav/subheading pattern, rather than copy-pasting a 4th time).

### Recently resolved (documented so it isn't re-investigated from scratch)
- The `403 Forbidden` / "request was not authenticated" issue on `getWaterFeatures`/`getSpeciesNearby`/`healthCheck` is fixed — every callable/HTTP function now deploys with `invoker: "public"` and its Cloud Run IAM policy correctly grants `allUsers` → `roles/run.invoker`. Verified directly via `gcloud run services get-iam-policy <fn> --region=us-central1 --project=survival-day-app`.
- The breadcrumb trail's "You" marker used to be a one-time location snapshot (only updated on page load or a manual refresh tap) instead of a live position — a user report ("the yellow dot doesn't follow me") led to fixing this, then a follow-up report ("still doesn't visibly move while recording") found the *real* underlying cause: the trail map's SVG viewBox was rescaling to fit the exact live position on every GPS tick, which visually masked real movement while the trail was actively growing. Both are fixed — see "Waypoints & Trail" above.
- A brand-new trial used to briefly show "4 days left" instead of "3" until the page was refreshed. Root cause: `trialDaysLeft` was computed with `Math.ceil()`, and right at trial start the true remaining time is as close to exactly 3.0 days as it'll ever be — any tiny clock skew between the server and the device pushed it just over the boundary. Fixed in `entitlement.ts` by clamping the displayed value to the actual granted trial length (derived from `trialEndsAt - createdAt`, both set together server-side, so immune to client clock skew of any size) instead of guessing at a buffer.
- Firebase Hosting was defaulting to a 1-hour cache on `index.html` and other app-shell files, meaning a correct deploy could take up to an hour to actually reach an already-visiting browser — several "you deployed but nothing changed" reports this session traced back to this, not to the deploy itself. Fixed with explicit `no-cache` headers on `**` and long-lived `immutable` caching scoped specifically to the content-hashed `/assets/**` files (ordering matters: Firebase Hosting applies the *last* matching header rule, not the most specific one).
- 3D Maps hung on "Loading map…" forever with no error. Root cause: MapLibre GL can't reliably locate its own background tile-parsing worker script via `import.meta.url` under Vite, so the worker silently failed on its first import — main-thread fetches succeeded normally, no `error` event ever fired, and `load` never fired either. Fixed with an explicit `setWorkerUrl()` pointer, imported via Vite's `?worker&url` (not plain `?url` — the worker imports a sibling chunk only `?worker&url` bundles alongside it).
- Terms of Service §8 still named **Open-Meteo** as a third party — stale since the Weather feature was removed back on 2026-09-07 (see "Removed features" below). Fixed 2026-09-09 while updating the Analytics-related legal copy; replaced with the app's actual current third parties (USGS, GBIF, Census Bureau, OpenFreeMap), matching what the Privacy Policy already listed. Worth periodically diffing Terms/Privacy's third-party lists against each other and against what's actually still integrated, since nothing currently enforces they stay in sync when a feature is removed.

### Known past bugs (fixed, documented so they aren't reintroduced)
- `firebase.json`'s functions `ignore` list used to include `"lib"`, which silently stripped compiled output out of every deploy (`lib/index.js does not exist` build failures). Removed — the ignore list should only ever contain `node_modules`, `.git`, and debug logs.
- `firebase-admin`/`firebase-functions` used to get installed as separate copies at the repo root vs. `functions/`, which silently broke Jest mocks (tests mocked one copy, real code used another). Fixed by converting to npm workspaces + pinning a shared `firebase-admin` version at the root.
- Hosting can upload files successfully but never "release" (activate) them if the overall `firebase deploy` command errors out afterward (e.g. on the Artifact Registry cleanup-policy nag) — check for "release complete" in the deploy log, not just "file upload complete."
- Styling a `<summary>` element with `display: flex` (or anything other than its default `list-item`) silently removes its native disclosure triangle in most browsers, even if `::marker` is separately styled — the marker box generation is tied to `display: list-item`. This made the Snares & Traps page's 100 collapsible trap-design cards look like plain, non-interactive text with no hint they could be tapped to reveal content. Fix: suppress the native marker explicitly (`list-style: none` plus `::-webkit-details-marker { display: none }` for Safari) and render your own toggle icon as part of the `<summary>` content instead of relying on browser marker behavior.
- A Dashboard icon (🪤, Snares & Traps) rendered as an empty box on the user's device. Cause: that emoji is Unicode 13.0 (2020) — recent enough that plenty of real devices/browsers don't have a font glyph for it yet. Fixed by swapping to an older, near-universally-supported emoji (🕸️, Unicode 9.0/2016) instead. Worth checking a new emoji's Unicode version before picking it for UI, not just how it renders on the machine doing the picking.
- `npm run test` (Vitest) does **not** type-check — it transpiles with esbuild, which strips types without validating them. A field-name typo in `searchIndex.ts` (referencing fields that don't exist on `TreatmentMethod`) passed every Vitest run as silent `undefined`s and only failed at runtime; `npm run build`'s real `tsc -b` step caught it immediately. Don't treat a green `npm test` alone as proof a new file type-checks — run the real build too before considering something done.
- A web-search-engine's own summarized answer for a factual lookup (a specific moonrise/moonset time, checking the Solunar Calculator's math) was flatly wrong — off by over an hour from the real published source. A direct fetch of the actual page it claimed to summarize showed the correct value and confirmed the app's own math was fine. Search-result summaries are a lossy paraphrase of something else, not a citation — verify against a direct fetch of the actual source before trusting a specific number from one, especially before concluding your own code is buggy because of it.

## Structure

This is an npm workspaces monorepo — one `npm install` at the root installs everything into a single deduped `node_modules` tree (this matters: `functions/` and `web/` used to get their own separate copies of shared packages, which silently broke Jest mocks in tests since the mock and the real code were different physical module instances).

- `web/` — React + TypeScript PWA (Vite), installable, with service worker precaching so most already-visited screens keep working without a live connection — signing in itself still requires one (Google Sign-In).
- `functions/` — Firebase Cloud Functions (TypeScript).
- `testing/functions/` — Tests for every Cloud Function, plus `check-coverage.js`, which CI runs on every PR to fail the build if any deployed function lacks a matching test.
- `firebase.json`, `.firebaserc`, `firestore.rules`, `storage.rules` — Firebase project config (project: `survival-day-app`).

## Workflow

All changes go through a branch → PR → CI (green) → merge. Nothing is pushed directly to `main`.

Every new Cloud Function added to `functions/src/` must have a corresponding test in `testing/functions/` referencing it by name, or CI will fail the `function-test-coverage` check.

Merging to `main` does **not** deploy — CI has no deploy step (see "Also open" above). A Claude Code session working on this repo commits/pushes/merges without asking for confirmation at each step once CI is green, but always asks before actually running `firebase deploy`, since that's the one step in the pipeline that's immediately outward-facing to real users.

Stripe and other secrets are stored in GitHub Actions secrets — never committed to this repo.
